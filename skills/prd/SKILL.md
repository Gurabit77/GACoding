# PRD Generator

创建清晰、可执行且适合 Gura 自动化开发的 PRD。

---

## 完整流程

```
Phase 1: 需求澄清 → Phase 2: 需求评审会（10+ story 时触发） → Phase 3: 写 PRD → Phase 4: 7轮自动审查 → Phase 5: 输出审查报告 → Phase 6: 自动衔接
```

---

## Phase 1: 需求澄清

1. 接收用户的功能描述
2. 提出澄清问题：
   - 数量不限，由需求复杂度和用户表达的明确程度决定
   - 只问用户必须决定的问题（产品方向、功能取舍、核心体验）
   - 技术决策自己做，在 PRD 里说明理由
   - 用自然语言提问，不用 ABCD 选择题格式
   - 用户已经说清楚的不要重复问
3. 用户回答后，**主动挖掘隐含需求**（不等用户催）：
   - 分析用户的使用场景，推导出用户没提但应该有的需求
   - 列出「你说的需求」+「我额外建议的需求」，让用户一次性确认
4. 如果还有拿不准的点，再确认（数量不限）

---

## Phase 2: 需求评审会

**触发条件**：预估 story 数量 ≥ 10 个，或用户主动要求。小项目（<10 story）可跳过。

1. 读取 `REVIEW_MEETING.md` 指令文件
2. 根据项目类型选择 5-8 个评审角色
3. 逐角色审视 Phase 1 产出的需求清单
4. 以产品总监身份逐条裁决（✅采纳 / ⚠️部分采纳 / ❌拒绝）
5. 将采纳的需求按 P0-P5 分层
6. 输出裁决清单给用户确认
7. 用户确认后，**以裁决清单（而非原始需求）作为 Phase 3 写 PRD 的输入**

**关键**：被拒绝的需求和理由也要记录在 PRD 的 Non-Goals 中，防止后续重复提出。

---

## Phase 3: 写 PRD 初稿

保存到 `tasks/prd-[feature-name].md`

### PRD 结构

1. **Introduction** — 功能描述、解决的问题、技术栈、项目路径
2. **Goals** — 具体可衡量的目标
3. **User Stories** — 每个 story 含：
   - 描述（"作为...我需要..."）
   - Acceptance Criteria（可验证的完成标准）
   - references（用户提供的参考链接或资料，如有）
4. **Functional Requirements** — 编号列表，明确无歧义
5. **Non-Goals** — 明确不做什么
6. **Design Considerations** — 视觉参考、Logo 方案、字体
7. **Technical Considerations** — 约束、依赖、兼容性
8. **Success Metrics** — 如何衡量成功
9. **Open Questions** — 剩余问题

### Story 编写规则

- 每个 story 足够小，能在一次 Agent 迭代内完成
- Acceptance Criteria 必须可验证，不能模糊
- 有 UI 变更的 story 加 "使用 agent-browser 在浏览器中验证"
- 如果用户提供了参考链接/资料，写入 references 字段

---

## Phase 4: 自动审查（必须执行，不可跳过）

PRD 初稿写完后，在给用户确认前，强制执行以下 7 轮审查。

**每轮必须输出具体检查结果**——不能只说「没问题」，必须列出「我检查了什么、发现了什么、改了什么/为什么不需要改」。

### Pass 1: 需求溯源
- 列出用户说过的每一条原始需求
- 逐条检查 PRD 是否覆盖，标注对应的 Story ID
- 任何未覆盖或被弱化的需求，立即补充
- 自动修正后继续

### Pass 2: Story 工程检查
- 检查 Story 之间是否有职责重叠
- 检查依赖顺序是否正确（priority 顺序）
- 检查每个 Story 的验收标准是否可验证
- 检查粒度：一个 Story 能否在一次 Agent 迭代内完成
- 自动修正后继续

### Pass 3: 边界条件检查
- 加载中状态是否有定义
- 错误处理是否覆盖
- 空数据场景是否考虑
- 极端情况是否处理
- 自动修正后继续

### Pass 4: 质疑优化空间
- 主动质疑当前方案是否还有优化空间
- 检查是否有更好的技术方案或交互设计
- 发现问题立即修正

### Pass 5: 第一性原理审查
- 回到项目的核心目标，检查每个 Story 是否真正服务于目标
- 是否有多余的 Story（做了但对目标没帮助）
- 是否有缺失的 Story（目标需要但没做）
- 发现问题立即修正

### Pass 6: 严格自我质疑
- 强烈质疑自己是否认真对待了这个项目
- 是否有偷懒、敷衍、遗漏的地方
- 是否全面挖掘了项目的可优化点
- 发现问题立即修正

### Pass 7: 四角色审查
- **用户视角**：模拟用户从打开页面到完成所有操作的完整路径，每一步检查是否有对应的 UI 和交互定义
- **设计师视角**：检查所有视觉元素是否有具体样式定义（颜色、尺寸、动画、状态变化），不能只写功能不写视觉
- **开发者视角**：检查技术可行性（依赖、兼容性、文件创建、接口参数），Builder Agent 拿到这个 Story 能不能直接开始写
- **产品视角**：检查需求闭环、边界条件、用户体验完整性
- 发现问题立即修正

### 最终自我追责确认
审查完成后，问自己：「确定现在没有遗漏了？很确定吗？你是这个项目的项目负责人，你要为结果负责，如果出了问题第一个追责的就是你！」

如果还有任何不确定的地方，继续修正直到完全确定。

---

## Phase 5: 输出审查报告

给用户看：
1. PRD 完整内容
2. 审查报告：7 轮审查中发现并修正了哪些问题、为什么改
3. 需求覆盖核对表（用户原始需求 vs Story ID）

---

## Phase 6: 自动衔接

用户确认 PRD 后：
1. 自动调用 gura skill 将 PRD 转成 prd.json
2. 转完后自动问用户：「prd.json 已生成（X 个 story），要启动 Gura 自动开发吗？选择 Agent：Claude / Kiro / Codex」
3. 用户确认后自动执行 `./gura.sh 项目路径`

---

## 项目类型检查清单（审查时参考）

根据项目类型，审查时额外检查：

**Web 项目：** 加载状态、错误处理、响应式布局、主题/暗色模式、无障碍
**API 项目：** 错误码规范、超时处理、并发、幂等性、文档
**CLI 工具：** 帮助文档、错误提示、退出码、配置文件

---

**重要提示：** 不要开始实施代码。只创建 PRD。
